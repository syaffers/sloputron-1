# Process: measurements, results.csv and CI

## The rule
Every commit that changes hardware (`rtl/`, `board/`) also adds a row per design to
`results.csv`. Rows are produced by the flow, never typed by hand.

```
make report NOTE="what changed and why the numbers moved"
git add -A && git commit
```

## Columns
| Column | Meaning |
|---|---|
| date | day of measurement |
| commit | HEAD the measurement was taken on, `+dirty` if uncommitted changes were included. A commit cannot contain its own hash, so a row describes the commit that adds it. |
| design | design name (= top module) |
| cells, cells_avail | nextpnr `ICESTORM_LC` used / available, post-placement |
| brams | nextpnr `ICESTORM_RAM` used |
| fmax_median, fmax_worst | MHz, `clk` domain, over `seeds` nextpnr seeds (1..N), target 100 MHz |
| seeds | number of seeds (≥ 16) |
| toolchain | OSS CAD Suite release; Yosys; nextpnr |
| bench_cycles, code_size | filled once a CPU runs the benchmarks (Phase 3+) |
| note | required whenever cells go up or median Fmax falls more than 2% |

## What CI checks (`make check`, `scripts/check_results.py`)
1. **Budget:** every design ≤ 1216 LC (95% of 1280) and ≤ 16 BRAMs.
2. **Not stale:** the fresh measurement matches the newest row for the design. Cells and
   BRAMs must match exactly (the flow is deterministic for a pinned toolchain); median
   Fmax must be within 1%.
3. **Present:** every design has at least one row.
4. **No silent regression:** versus the previous row, more cells or a > 2% Fmax drop
   needs a non-empty `note`.
5. **A row per hardware change:** if `rtl/` or `board/` changed since `HEAD^`,
   `results.csv` changed too.

CI also lints, runs the self-checking simulations and uploads the bitstreams.

## Adding a design
Add it to the registry at the top of the `Makefile`:
```
DESIGNS += foo
foo_SRC := rtl/.../foo.sv ...
foo_TB  := sim/foo_tb.sv          # optional, self-checking, prints PASS / $fatal
```
The top module must be named after the design and use the port names in
`board/icestick.pcf`.

## Hardware Fmax confirmation
nextpnr's Fmax is an estimate until it has been confirmed on the board with a PLL sweep.
The harness for that (self-checking design + PLL configurations generated by `icepll`)
arrives with the first CPU skeleton; until then, nextpnr Fmax is labelled as such.
